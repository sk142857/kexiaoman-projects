# 课小满 多租户设计方案（面向家长）

> 背景：课小满（学习打卡小程序）当前 `t_lp_*` 业务数据全局共享，管理员可查看**所有**学生/任务/合集，
> 无租户维度。为支持「面向家长」的多租户模式，本文给出租户模型、数据隔离、权限控制、注册绑定与后台改造方案。
>
> 核心原则：
> - **租户 = 家长**：一个家长 = 一个家庭数据域（一个租户），数据天然按家庭隔离。
> - **一人一租户**：所有账号（家长 / 孩子）只能唯一归属一个租户。
> - **服务端强制隔离**：所有 `/api/lp/*` 查询必须按租户过滤，不依赖前端隐藏。

---

## 1. 租户模型

```
租户 t_lp_tenants（= 家长家庭数据域）
 ├── 家长（租户主，1 个，role=admin，owner_staff_id）
 └── 孩子（role=student，N 个）

隔离范围：任务 / 打卡 / 合集 / 学生列表 / 绑定映射 / 订阅授权 / 业务时间轴 / 仪表盘 全部按租户隔离。
```

- 每个账号（`t_staff`）唯一归属一个租户，`tenant_id` 决定其可见数据域。
- 家长账号在小程序端的行为类似当前「管理员」：可查看/管理本租户内全部孩子、任务与打卡审核。
- 平台超级管理员（如 `sys_admin`）不归属具体租户（`tenant_id=0`），可跨租户查看与维护。

### 1.1 角色语义调整

当前 `t_staff.staff_role` 只有 `admin | student`，其中 `admin` 在小程序端=全量管理员。引入租户后需区分：

| 角色 | 归属 | 数据范围 | 后台可见菜单 |
|------|------|---------|-------------|
| 平台管理员 | `tenant_id=0` | 全部租户（可筛选/管理） | 全部菜单 |
| 家长（租户管理员） | `tenant_id > 0` | 仅本租户 | 仅学习管理（本租户数据） |
| 学生（孩子） | `tenant_id > 0` | 仅本租户内自己的任务/打卡 | 仅学习仪表盘 |

> 实现建议：不新增角色枚举，用「`staff_role=admin` + `tenant_id>0`」判定家长角色；
> 菜单按角色返回时对 `tenant_id>0` 的 admin 收敛到学习管理分组（复用现有 `requireModulePermission` + 菜单配置）。

## 2. 数据模型改造

### 2.1 新增表 `t_lp_tenants`

| 列 | 类型 | 说明 |
|----|------|------|
| `tenant_id` | BIGINT PK | 序列 `tenant_id` 发放 |
| `tenant_name` | VARCHAR(64) | 家长姓名 / 家庭名 |
| `owner_staff_id` | BIGINT | 家长账号 `staff_id`（租户主） |
| `tenant_status` | TINYINT | 1 启用 / 0 停用（停用即锁定名下全部账号） |
| `created_at` / `updated_at` | DATETIME | 时间戳 |

> 索引：`idx_owner (owner_staff_id)`。

### 2.2 归属列（账号→租户）

二选一，本文推荐 **方案 A**（一人一租户，直列最简单，唯一约束兜底）：

- **方案 A**：`t_staff` 新增 `tenant_id BIGINT NOT NULL DEFAULT 0` + 索引 `idx_staff_tenant (tenant_id)`。
  缺点：`t_staff` 是跨小程序共享系统表，会带上仅课小满语义的列（`0` 表示不归属）。
- **方案 B**（保持共享表干净）：新增映射表 `t_lp_tenant_members (staff_id PK, tenant_id)`，`staff_id` 唯一约束保证一人一租户。
  缺点：查询多一次 join，`lpAuth` 每次要解析归属。

### 2.3 业务表加 `tenant_id`（冗余列 + 索引）

| 表 | 说明 | 写入时机 |
|----|------|---------|
| `t_lp_tasks` | 任务 | 创建时取 `created_by` 的 tenant |
| `t_lp_task_checkins` | 打卡 | 随所属任务的 tenant |
| `t_lp_task_collections` | 合集 | 创建时取创建者 tenant |
| `t_lp_task_timeline` | 业务时间轴 | 随业务对象 tenant |
| `t_lp_task_assignees` | 任务派发 | 随任务 tenant（或经任务 join） |

均加 `idx_tenant (tenant_id)`。冗余列的价值：查询/聚合（待审核列表、仪表盘）**免 join 直接按租户过滤**，隔离逻辑统一且不易漏。

> `t_lp_students`（openid↔staff 绑定）与 `t_lp_subscribe_grants`（订阅授权）**不新增** tenant_id，
> 租户经 `staff.tenant_id` 派生即可；如后续查询量大有性能需求，可冗余（写入时随 staff 带出）。

### 2.4 序列

`t_seqs` 增加 `tenant_id` 序列（与 `task_id`/`staff_id` 等一致，`nextSeq("tenant_id")` 发放）。

### 2.5 存量数据迁移（`upgrade_NNN_lp_tenant.sql`，幂等）

1. `CREATE TABLE IF NOT EXISTS t_lp_tenants`。
2. `t_staff` 加 `tenant_id` 列 + 索引（`information_schema` 判空，幂等）。
3. 各 `t_lp_*` 业务表加 `tenant_id` 列 + 索引。
4. **默认租户兜底**：插入 `t_lp_tenants(tenant_id=1, tenant_name='默认租户', owner_staff_id=0)`。
5. `UPDATE t_staff SET tenant_id=1 WHERE tenant_id=0`；各业务表 `SET tenant_id=1`（存量全部归默认租户）。
6. 同步 `t_seqs` 的 `tenant_id`（下次发放 ≥ 2）。

> ⚠️ 存量数据无法按家长自动分组（现有关联只有 `task_assignees`，没有「家长↔孩子」关系），
> 因此统一归入默认租户，再由后台「租户管理」的人工迁移工具拆分（见 §5）。

## 3. 权限与访问控制（隔离核心）

### 3.1 身份解析（`lpAuth.js`）

- 登录 / 绑定时解析出当前 staff 的 `tenant_id`。
- `req.lp = { staffId, openid, role, tenantId }`。
- 锁定判定增加租户维度：`tenant` 停用、账号不归属任何有效租户 → 直接 403。

### 3.2 强制隔离点（`routes/lp.js` 等，全部服务端强制）

| 接口 | 现状 | 多租户改造 |
|------|------|-----------|
| `GET /tasks` `detail` `copy` `update` `status` `delete` | 按派发/创建人可见 | 查询先 `.eq("tenant_id", tenantId)`；对 `task_id` 二次校验归属 |
| `GET /checkins`、`POST /checkins/*` | 按 `created_by` | 打卡表带 tenant 过滤；提交时校验任务归属本租户 |
| `GET /admin/students` | **全量学生** | 只返回本租户学生（家长视角）；平台管理员可按租户筛选 |
| `GET /todos`（admin 待审核） | **全量待审打卡** | 只查本租户任务下的打卡；审核接口二次校验被审记录归属 |
| `GET /collections` `create` `update` `delete` | 列表是**免登录白名单**（`PUBLIC_LP_PATHS`） | **从白名单移除**（免登录只读与租户隔离冲突）；改登录鉴权 + 按租户过滤 |
| `GET /dashboard`、订阅相关 | 按 staff | 仪表盘/订阅授权按租户收敛（订阅发送目标仅限本租户 openid） |
| `POST /upload` | 按 openid | 写入 `file_uploads` 时带 tenant（可选），图片归属随业务 |

### 3.3 交叉租户风险点（重点防越权）

- 所有**按主键直达**的接口（`task_id` / `checkin_id` / `collection_id`）必须在 `lpAuth` 之后做 `tenant_id` 归属校验，
  不能只依赖前端不显示入口。
- `viewStaffId`（管理员切换视角）只能切换到**本租户内**的 `student`。
- 时间轴、仪表盘聚合、订阅通知的 `openid` 解析全部限定在本租户内，防跨租户数据泄露。

## 4. 注册与绑定流程（面向家长）

沿用现有「邀请码绑定」机制，扩展租户语义：

```
1. 开通：后台创建家长账号（role=admin）→ 系统自动建租户
        （tenant_name=家长名，owner_staff_id=家长账号）+ 自动生成家长邀请码
   或：家长自助注册（输入运营发放的开通码）→ 建租户 + 家长账号 + 家长邀请码
2. 添加孩子：家长在小程序 / 后台为孩子创建 student 账号（归属同一租户）→ 生成孩子邀请码
3. 绑定：孩子输入「孩子邀请码」绑定 → 归属其租户；
        家长输入「家长邀请码」绑定 → 以家长（租户管理员）身份进入
4. 一人一租户约束：openid 已绑定租户 A 时，换绑到租户 B 账号需显式解绑确认（跨租户迁移，防误操作）
```

- 邀请码生成/作废逻辑不变（`t_staff.invite_code`），绑定成功后 `tenant_id` 随账号归属确定。
- `findStaffByInviteCode` 绑定判定增加租户维度校验（家长码只能被家长绑定、孩子码只能被孩子绑定，按 `staff_role` 区分）。

## 5. 后台改造

### 5.1 新增「租户管理」模块（归属「学习管理」分组，复用通用 CRUD）

- 列表：租户名 / 家长账号 / 孩子数 / 任务数 / 状态。
- 操作：详情、停用/启用（停用即锁定租户内全部账号）、删除。
- **迁移工具**：把指定账号 / 其名下数据从「默认租户」迁入目标租户（面向家长场景的初始化拆分）。

### 5.2 学习模块按租户筛选

- 任务 / 打卡 / 合集 / 绑定管理：列表增加「按租户筛选」（平台管理员可用）。
- 家长（`tenant_id>0` 的 admin）登录后台：数据默认锁定本租户，看不到租户筛选器。

### 5.3 菜单与角色收敛

- `role=admin` + `tenant_id>0`（家长）登录后台：菜单仅返回「学习管理」分组（复用 `ensureDefaultMenus` /
  `requireModulePermission`），不暴露系统设置 / 管理员管理 / 小程序配置。
- 平台超级管理员保持全菜单。

## 6. 分阶段实施计划

| 阶段 | 内容 | 涉及文件 |
|------|------|---------|
| 一、数据层 | 建 `t_lp_tenants`、加列、默认租户迁移、`t_seqs` | `sql/upgrade_NNN_lp_tenant.sql`、`init_schema.sql`、`tables.js` |
| 二、小程序端隔离 | `lpAuth` 注入 `tenantId`；`lp.js` 全部查询按租户过滤；`viewStaffId`/审核/合集收敛 | `routes/lpAuth.js`、`routes/lp.js`、`learningLib.js` |
| 三、后台 | 「租户管理」菜单 + 迁移工具 + 学习模块租户筛选 + 家长菜单收敛 | `routes/admin.js`、`routes/adminApi.js`、`admin/config/modules.jsx` |
| 四、开通流程 | 家长注册/开通 + 孩子账号创建 + 绑定租户约束 | `routes/lpAuth.js`、小程序 `pages/bind` |

## 7. 风险与注意事项

1. **存量数据归属**：无法自动按家长分组，默认租户兜底后需人工迁移（阶段三的迁移工具承载）。
2. **公开白名单接口**：`/collections` 当前免登录只读，与租户隔离直接冲突，**必须**下线白名单并改登录鉴权。
3. **共享表污染**：方案 A 给 `t_staff` 加 `tenant_id` 会出现在跨小程序共享表；如介意改用方案 B 映射表。
4. **越权面**：所有按主键直达的接口都要二次校验 `tenant_id`；审核、订阅通知的 openid 只限本租户。
5. **订阅消息模板**：`subscribe_tmpl_ids` 等配置在 `t_apps`，属平台级，与租户无关，无需改。
6. **升级脚本规范**：加列走 `information_schema` 判空的幂等写法，禁止直接改已上线库结构。
