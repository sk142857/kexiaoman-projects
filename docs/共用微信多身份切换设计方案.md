# 课小满 共用微信多身份切换设计方案

> 状态：**已落地实现**（迁移 SQL / 后端接口 / 前端入口 / PIN 管理均已实现，待真机回归）。
> 背景：小学生大多没有自己的手机，常与家长共用一台手机（**同一微信号 / 同一 openid**），
> 但课小满当前是「一 openid 绑定一身份、绑定后一次性锁定」模型，家长与孩子无法在同一微信号上共存并切换。
> 同时必须兼容「家长、学生各有手机」（各自 openid 各绑一个身份）的既有场景。
>
> 核心原则：
> - **一 openid 多绑定（1:N）+ 活动身份切换**：同一 openid 可同时绑定主家长 + 多个孩子（+家属）身份，通过「活动身份」切换。
> - **业务数据天然按 staff_id 隔离**：切换身份 = 换 token 里的 staffId，业务路由零改动。
> - **家长身份受 PIN 锁保护**：孩子切到家长模式需 PIN（家长自选开启），防止越权查看敏感信息。
> - **服务端强制校验**：所有切换/PIN 校验在服务端完成，不依赖前端隐藏。

---

## 1. 现状与问题

### 1.1 现状模型（一 openid 一身份）

| 项 | 现状 |
|----|------|
| 绑定表 | `t_lp_students`，唯一键 `uk_app_openid (app_id, openid)`，**一 openid 只能绑定一个 staff** |
| 身份锁定 | 绑定后一次性锁定（换绑需 `rebind` 显式解除） |
| 登录 | `POST /api/lp/login`（wx.login code → code2session → openid），JWT 仅含 `{ openid, appId }` |
| 鉴权 | `lpAuth` 中间件每次请求按 openid 解析出**唯一** staff_id / role / scope |
| 角色 | `admin` / `parent` / `family` / `student` |
| 数据隔离 | 任务/打卡/合集按 `created_by` + `task_assignees` + `familyScope` 收敛 |

### 1.2 目标场景

```
场景A（共用微信）        场景B（各有手机，现状已满足，需保持）
家长 ─┐                   家长 openid P ── 家长身份
      └─ 同一 openid ──►  孩子 openid C ── 孩子身份
孩子 ─┘  家长身份 + 孩子身份（可切换）
```

- 场景 A：家长先绑定家长身份 → 生成孩子学生码 → 同一 openid 再绑定孩子身份 → 两身份随时切换；孩子切家长模式需 PIN。
- 场景 B：行为与现状完全一致（`identities` 仅 1 条，前端无切换 UI）。

## 2. 总体设计

```
┌────────────────────────────────────────────────────┐
│ 一个 openid（共用微信）                               │
│   ├─ staff_id=9001  parent   主家长  🔒 PIN         │
│   ├─ staff_id=9002  student  孩子A                   │
│   └─ staff_id=9003  student  孩子B                   │
│   多个有效绑定共存；JWT 中 staffId 指明「当前活动身份」  │
└────────────────────────────────────────────────────┘
```

- **多绑定**：`t_lp_students` 唯一键放开为 `(app_id, openid, staff_id)`，同一 openid 可绑多个身份。
- **活动身份**：JWT payload 增加 `staffId`；切换 = 服务端签发新 token。
- **实时复核保留**：`lpAuth` 每次请求校验「(openid, staffId) 绑定有效 + staff 在职」，作废/锁定立即生效。
- **PIN 锁**：仅 `parent`/`admin` 身份可设；`switch` 切到受保护身份时必须携带正确 PIN。

## 3. 数据模型

### 3.1 `t_lp_students` 唯一键调整

```sql
-- 原：UNIQUE KEY uk_app_openid (app_id, openid)
-- 新：同一 openid 可绑多个 staff；同一 (openid, staff) 不重复
UNIQUE KEY uk_app_openid_staff (app_id, openid, staff_id)
```

- `id / staff_id / app_id / openid / bound_at / bound_status / created_at / updated_at` 不变。
- `bound_status=0` 仍为「作废/锁定」；`lpAuth` 实时复核某条具体绑定。

### 3.2 `t_staff` 增加 PIN 字段

```sql
ALTER TABLE t_staff ADD COLUMN pin_hash VARCHAR(100) NOT NULL DEFAULT ''
  COMMENT '身份切换 PIN（bcrypt，仅 parent/admin 可设，空=未开启）';
```

- PIN **归属身份本身**（而非 openid）：无论从哪个手机（哪个 openid）切到该家长身份，都要 PIN。
- 用 bcrypt 存哈希；4-6 位数字。
- 亦可独立表 `t_lp_identity_locks(app_id, staff_id, pin_hash)`（若不愿污染共享系统表 `t_staff`，参考多租户方案的方案 B 取舍）；本方案默认用 `t_staff.pin_hash`。

### 3.3 （可选）`t_lp_active_identity`

记录 openid 最近活动身份（`openid` PK / `(app_id, openid)` PK，`staff_id`），供冷启动默认身份恢复；
亦可由前端 `storage` 保存 `lp_active_staff_id` 承担，本方案默认走前端 storage，不建表。

## 4. 后端接口

### 4.1 `POST /api/lp/login`（改造）

- 请求：`{ code, activeStaffId? }`（前端传上次活动身份，无则后端默认）。
- 响应（多绑定时代）：

```json
{
  "code": 0,
  "data": {
    "token": "<JWT: {openid, appId, staffId}>",
    "bound": true,
    "activeStaffId": "9001",
    "identities": [
      { "staff_id": "9001", "role": "parent", "nickname": "…", "pin_enabled": true },
      { "staff_id": "9002", "role": "student", "nickname": "…", "pin_enabled": false }
    ]
  }
}
```

- 无绑定 → `bound:false`（前端身份选择页）。
- 单绑定 → 行为与现状一致（`identities` 长度 1）。
- 多绑定 → 返回全部有效身份；`activeStaffId` 优先取前端传入且仍有效的，否则取「上次默认 / 首个有效身份」。

### 4.2 `POST /api/lp/switch`（新增）

```
请求：{ staffId, pin? }        // 会话 token 鉴权
逻辑：
1. 校验 (app_id, openid, staffId) 绑定有效 + staff 在职；越权/失效 → 403/401。
2. 目标 staff_role ∈ {parent, admin} 且已设 pin_hash：
     → 必须携带 pin 且 bcrypt 校验通过，否则 403「PIN 错误」（带 need_pin 标记可前端预判）。
3. 通过 → 签发新 JWT（含新 staffId）→ { token, role, staff, identities }。
切到 student / family 无需 PIN。
```

### 4.3 `POST /api/lp/pin`（新增，三种子操作）

```
{ action: "set",   pin }   // 设置/修改（仅 parent/admin，本身份操作自己）
{ action: "verify", pin }  // 校验（供前端预检/错误提示）
{ action: "remove", pin }  // 关闭（需正确 PIN；关闭前前端二次确认风险）
```

- 4-6 位数字，服务端校验格式 + bcrypt 存储。

### 4.4 `POST /api/lp/bind`（改造）

- 由「已绑定其他身份 → 拒绝」改为「**追加绑定**」：绑定不同 staff 时新增一行，返回新 token + `identities`（活动身份自动切到新身份）。
- 保留 `rebind` 作显式换绑兜底（覆盖某条绑定）。
- 学生码仍单次使用；共用手机需给孩子「新设备」再绑时，家长重新生成学生码即可（`family/children/invite` 已支持）。

### 4.5 `GET /api/lp/session`（保持）

返回 `{ role, staffId }`；会话心跳实时复核语义不变。

## 5. 鉴权中间件（`lpAuth.js`）

```
现状：decode token → openid → 查 lp_students（按 openid 单行）→ staff → role/scope
改后：decode token → openid + staffId
       → 校验 (app_id, openid, staffId) 绑定存在且 bound_status=1
       → 校验 staff 在职
       → familyScope(staffId, role) 计算 scope（逻辑不变）
```

- **实时复核保留**：每次请求复核具体绑定，后台作废某条绑定 → 对应身份立即失效。
- **老 token 兼容**：旧 JWT 无 `staffId` → 视为未绑定态，返回 401 → 前端 `ensureLogin` 自动重新登录刷新为带 staffId 的新 token。

## 6. 前端改动

### 6.1 `utils/api.js`

- 新增 `lpAuth.switch(staffId, pin)`、`lpAuth.pinSet(pin)`、`lpAuth.pinVerify(pin)`、`lpAuth.pinRemove(pin)`。
- `lpAuth.login()` 透传 `activeStaffId`（读取 storage `lp_active_staff_id`）。
- 新增存取 `lp_active_staff_id`。

### 6.2 `app.js` `ensureLogin`

- login 后：
  - `identities.length === 1` → 现状逻辑（直接进首页）。
  - `identities.length > 1` → 从 storage 取 `lp_active_staff_id`；有效则作为活动身份进入首页，无效则展示**身份选择器**（或默认家长身份进首页 + 提示切换）。
- 切换身份后清 `lp_view_staff_id`（家长「查看学生视图」残留）。

### 6.3 「我的」页 `mine`（新增两块）

1. **身份切换卡片**：`identities.length > 1` 时展示，列出可切换身份，当前身份打角标；点击切身份 → 调 `switch`（家长身份需 PIN 弹窗）。
2. **PIN 风险卡片**（顶部，可关闭）：多身份 + 家长身份未设 PIN 时展示：

   > ⚠️ 本机同时绑定了「家长 + 孩子」身份，未开启 PIN 锁，孩子可一键切换到家长身份，查看家庭信息、后台账号、家属共享等敏感内容。 [立即开启] [暂不开启]

   已设 PIN → 显示「🔒 已开启身份保护」。

### 6.4 设置页 `pkg-mine/settings`

- 新增「身份保护」菜单项（仅 parent/admin）：开启 / 修改 / 关闭 PIN；关闭时二次确认风险弹窗。

### 6.5 绑定完成页 `identity`

- 绑定后若形成多身份（如家长已绑、再绑孩子），完成步弹风险提示：

  > ⚠️ 检测到您与孩子共用此微信。未开启 PIN 锁时，孩子可自行切换到「家长」身份，查看家庭信息、后台账号、家属共享等敏感内容。建议开启 PIN 锁保护（仅家长知道密码）。 [开启 PIN 锁] [暂不开启]

  「暂不开启」跳过，后续可到设置页随时开启。

### 6.6 切换身份时的 PIN 弹窗

- 目标身份为 parent/admin 且 `pin_enabled=true` → 弹 PIN 输入（6 位数字键盘），错误提示「PIN 错误，请重试」。

## 7. PIN 锁（家长自选）

**四触点 + 一校验：**

| 触点 | 位置 | 行为 |
|------|------|------|
| ① 首次形成多身份 | 绑定完成页 | 弹窗提示风险，「开启 / 暂不开启」 |
| ② 常驻风险卡 | 「我的」页顶部 | 未设 PIN 时展示，引导开启（可关闭） |
| ③ 管理入口 | 设置页「身份保护」 | 随时开启 / 修改 / 关闭 |
| ④ 切换强校验 | `switch` 到 parent/admin | 服务端 bcrypt 校验 PIN，错误拒绝 |

**安全说明**：
- PIN 存服务端（bcrypt），`switch` 内校验，前端无法绕过。
- 仅影响「切到家长/管理员」方向；切到孩子/家属无需 PIN（家长交手机给孩子不受阻）。
- 关闭 PIN 需先验证正确 PIN + 前端二次确认。

## 10. 安全与边界

1. **切换鉴权**：只能切到本 openid 有效绑定的身份，`switch` 服务端强校验（openid + staffId）。
2. **PIN 防绕过**：bcrypt 存服务端、`switch` 内校验；孩子无法通过清缓存 / 抓包绕过。
3. **邀请码门禁不变**：新增身份仍需有效邀请码（学生码只能绑对应孩子、家长码/注册建家长），天然限制随意绑定他人账号。
4. **数量上限**：单 openid 绑定数建议 ≤6（`bind` 内软限制，防滥用）。
5. **通知/提醒**：同一学生多 openid（家长手机 + 孩子手机）时，审核结果 / 打卡提醒全员可达。
6. **共用手机 UX**：家长切孩子 → 交手机；孩子切家长 → 需 PIN（未设 PIN 时家长需知晓风险，前端已提示）。

## 12. 风险与注意事项

1. **共享表污染**：`t_staff.pin_hash` 会带上课小满语义到跨小程序共享系统表；介意可改独立表 `t_lp_identity_locks`。
2. **通知去重**：同一学生多 openid 时，订阅消息可能重复触达（家长手机 + 孩子手机），需按 openid 独立判断次数/去重。
3. **默认活动身份**：冷启动无 `activeStaffId` 时的默认选择需谨慎（建议默认家长，避免孩子机主视角误进；或弹选择器）。
4. **升级脚本规范**：加列走 `information_schema` 判空幂等写法，禁止直接改已上线库结构。
5. **PIN 遗忘**：无找回机制（同微信内本身份），可「重新绑定」或后台重置（后台可清空 pin_hash）。
